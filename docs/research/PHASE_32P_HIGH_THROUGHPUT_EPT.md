# Phase 32P High-Throughput EPT Execution

## Finding

The frozen 414.636 ha production fixture contains 27 disconnected polygon components. Phase 32O produced 50 regions because cell alignment used `floor`/`ceil` boundaries but advanced with a rounded target width. A 701-cell span with a 700-cell step therefore became a 700-cell region plus a one-cell sliver. Buffers amplified those slivers by as much as roughly 180 times.

The larger cost was below the planner. Every parent EPT read wider or taller than 500 m was split again into 100 m subreads. Each subread started a fresh managed Python process, performed a separate EPT read, ran PyForestScan, and wrote an intermediate raster. A representative 700 x 560 m parent therefore required about 42 complete scientific operations. One observed parent spent 493.609 seconds in bounded read and CHM generation, while core extraction took 0.110 seconds and checkpoint/checksum work took 0.015 seconds.

## Production Policy

- The adaptive planner now classifies a complete component as safe using its calculated point, raster-cell, and memory budgets instead of a fixed three-million-point ceiling.
- Aligned subdivisions use balanced integer ranges. Rounding can no longer leave one- or two-cell residual regions.
- Ordinary EPT regions up to 2,000 m per axis and 6 GiB estimated memory execute as one managed operation.
- Nested isolation remains available for genuinely large regions. Its checkpoint core increases from 100 to 500 cells, reducing process and EPT request overhead while preserving recovery.
- The pilot resolves the HAG contract once. Production work units do not repeat suitability inspection.

## Telemetry

Each CHM work unit writes `diagnostics/science_timing.json` with process identity, point count, EPT read/decode, array merge, HAG contract, PyForestScan CHM, buffered raster write, and total elapsed time. Coordinator snapshots also carry the active work-unit ID so UI progress can identify the region doing work.

This instrumentation measures production stages without changing PyForestScan scientific calculations.

## Completed Phase 32O Baseline

The preserved run completed all 50 regions with zero failures in 3,711.453 seconds. Forty-nine regions emitted timing files and one completed as valid NoData. The machine-readable summary is [PHASE_32P_PRODUCTION_TIMING_BASELINE.json](PHASE_32P_PRODUCTION_TIMING_BASELINE.json).

| Bounded EPT read + PyForestScan CHM | 46.515 s | 105.531 s | 153.110 s | 245.719 s |
| Core extraction | 0.031 s | 0.063 s | 0.094 s | 0.140 s |

The bounded read/CHM stage accounts for 3,503.561 of 3,508.543 summed work-unit seconds. Core extraction and durable state are negligible by comparison. Phase 32P adds the deeper EPT-read, point-decode, PyForestScan, and raster-write split for new runs.

## Authoritative Call Graph

`Mission Control -> polygon Prerun -> SourceAwareWorkPlanner -> managed Processing Engine -> detached polygon_job_coordinator -> bounded EPT read -> PyForestScan calculate_chm -> core extraction -> checkpoint -> mosaic -> exact polygon mask -> output registration/load`

There is no fallback from component-aware EPT planning to the retired envelope-grid planner, no source-wide EPT materialization path, and no synchronous QGIS-thread science fallback. Internal `SkippedOutsidePolygon` state remains only for non-EPT compatibility/recovery contracts; sparse EPT planning does not create those records.

## Legacy Audit

- `External Worker` remains disabled and appears only in its guardrail/research implementation and Advanced Batch disclosure.
- PBM/backend terms remain in setup, technical diagnostics, and implementation boundaries; normal processing uses Processing Engine terminology.
- `SkippedOutsidePolygon` remains a durable compatibility enum for older/local plans, not normal-user copy and not sparse EPT materialization.
- No global-envelope EPT fallback, generic source-wide EPT preparation, or coordinator-to-synchronous-science fallback was found in the production call graph.
- Managed workspaces remain in the existing durable job root. Moving them under `%LOCALAPPDATA%/PyForestScan/jobs/<job-id>` is deferred to Phase 32Q so storage migration cannot destabilize this throughput repair.
